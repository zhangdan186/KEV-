## 第 2 页：问题背景与任务目标

### 页面标题

**问题背景与分析目标**

### 页面正文

```text
CISA KEV 目录记录了具有可靠在野利用证据的漏洞。

本题需要回答：
1. 目录数据的结构和质量是否可靠？
2. 漏洞加入目录的时间和处置期限如何分布？
3. 厂商、产品和 CWE 标签呈现怎样的记录结构？
4. 能否对日期、厂商、勒索状态和 CWE 进行组合查询？

分析边界：
- 结论只适用于课程提供的本地快照；
- KEV 记录数不等于攻击次数或漏洞严重程度；
- Unknown 表示尚未确认，不表示没有被勒索软件利用。
```

### 页面视觉

采用“数据输入 → 数据质量 → 分析与查询 → 可视化”的横向流程，右下角放置三条分析边界警示。

### 主讲提示

KEV 是优先处置目录，而不是完整漏洞数据库。我们首先保证数据结构和字段语义正确，再开展统计和可视化，避免在错误数据或错误语义上进行分析。

## 第 4 页：系统总体架构与技术路线

### 页面标题

**从原始 JSON 到可复现分析结果**

### 页面正文

```text
原始 CISA KEV JSON
        |
        v
Loader：读取元数据和 vulnerabilities 数组
        |
        v
Validator：字段、格式、日期、枚举和黄金计数
        |
        v
Cleaner：保留原字段，生成 clean 和分析字段
        |
        +------------------+------------------+------------------+
        v                  v                  v                  v
   时间/期限/状态      厂商与集中度        CWE与查询       TF-IDF + KMeans
        |                  |                  |                  |
        +------------------+------------------+------------------+
                                   v
                         Exporter + Manifest
                                   |
                         CSV / PNG / HTML / GUI
```

### 页面要点

- `Prepared DataFrame` 是三人模块之间的公共接口；
- 分析模块不直接读取其他模块的 CSV；
- GUI 读取原始 JSON，并复用公共 Loader、Validator、Cleaner；
- `main.py` 只负责流程编排，不重复实现统计公式；
- `run_manifest.json` 记录输入和输出哈希，保证结果可追溯。

### 页面视觉

使用单向数据流图，验证失败分支用红色箭头指向“校验报告/终止”，分析模块使用四个并列节点，底部统一连接到输出层。

### 主讲提示

架构的核心是单一事实源：原始 JSON 只读取一次，验证和清洗由公共模块完成，后续成员基于同一个 Prepared DataFrame 开展工作。这样可以避免每个人使用不同的字段清洗和统计口径。

## 第 5 页：数据读取、清洗与验证

### 页面标题

**数据质量控制：先验证，再清洗**

### 页面正文

#### 读取结果

```text
目录版本：2026.07.29
原始记录：1,656 条
顶层字段：5 个
漏洞原始字段：11 个
count 与实际记录数：一致
```

#### 验证结果

| 检查项 | 结果 |
|---|---:|
| CVE 非空且唯一 | 通过，1,656 个唯一值 |
| 日期格式和日期顺序 | 通过，错误数为 0 |
| Known/Unknown 枚举 | 通过，非法值为 0 |
| CWE 列表和成员格式 | 通过，错误数为 0 |
| 关键文本完整性 | 通过，空值/空字符串为 0 |
| 空 CWE | 171 条，保留原状 |

#### 清洗原则

```text
原字段不覆盖
vendorProject/product 仅去除首尾空格
生成 vendor_clean/product_clean
cwes 在内存中保持 list[str]
不进行模糊匹配、拼写纠正或主观合并
```

### 页面视觉

- 左侧展示“读取 → 验证 → 清洗”的三步流程；
- 右侧放置验证结果表；
- 底部用一行强调：`kev_prepared.csv` 是后续模块共享的准备数据，而不是 GUI 的上传输入。

### 数据来源

- `outputs/validation/metadata.json`
- `outputs/validation/validation_summary.csv`
- `outputs/validation/field_profile.csv`
- `outputs/prepared/kev_prepared.csv`

### 主讲提示

验证器不修改原始数据，清洗器返回独立副本。题目明确要求空 CWE 记录继续保留，因此不能把空列表填成虚构的 CWE。厂商和产品只去除首尾空格，避免引入主观的实体归并。

## 7. PPT制作统一要求

- 所有数字从 `outputs/` 读取，禁止手工抄算后修改；
- 每张图表标注数据来源文件名；
- 报告和 PPT 中统一使用 `Known`、`Unknown`、`已确认`、`尚未确认`；
- 比例在 PPT 中显示为百分数，但 CSV 中保持 `[0,1]` 小数；
- 代码只展示 Loader、Validator、Cleaner 的少量关键片段，不展示完整文件；
- 使用大字号、短句和流程图，避免把报告段落直接复制到幻灯片；
- 最终 PPT 应准备 PNG 截图作为 GUI 故障时的离线演示材料。
